# Major Decisions

These are the decisions that will influence the entire project.

### Identity

* Project Name: **AstraAtlas**
* Tagline: **Open. Verified. Trusted.**


### Mission

Build an open, trustworthy, professionally engineered platform for verified space data sourced from official organizations.


### Guiding Principles

1. Official Sources
2. Open Source First
3. Professional Engineering
4. Trust by Design
5. Stewardship for the Future


### Roadmap

We adopted an **Era-based**, **Capability-driven** roadmap instead of a feature checklist.

That decision will help us prioritize long-term platform maturity over short-term feature accumulation.


### Architecture

We adopted:

* Layered Architecture
* Connector Architecture
* Trust Engine
* Data Pipeline
* Domain-first design


### Technology

We selected technologies based on:

* Long-term maintainability
* Open-source ecosystem
* Reliability
* Security
* Cost (free-first)
* Community support

—not popularity.


### Documentation

Documentation is part of the Definition of Done and evolves alongside the code.


### Development Standards

We established standards for:

* Git
* Commits
* Branches
* Reviews
* Testing
* Security
* Logging
* Documentation

Before implementation begins.


# What Went Well

I think several decisions stand out as particularly strong:

* Starting with a Constitution before code.
* Treating trust as a first-class architectural concern.
* Choosing technologies based on principles rather than trends.
* Designing for extensibility without over-engineering.
* Keeping the project accessible by relying on free and open-source tools.
* Thinking about the platform in terms of eras and capabilities.

These choices give AstraAtlas a clear identity.


# Lessons Learned

A few themes emerged repeatedly:

* Trust is not a feature—it is an architectural property.
* Documentation is an engineering asset.
* Simplicity before scale prevents unnecessary complexity.
* Long-term thinking leads to better technical decisions.
* A project’s philosophy influences its implementation.


# Risks

Every project has risks, even before code exists.

We’ve already identified a few:

* Official sources may change APIs or website structures.
* Some agencies may not expose structured data.
* Connectors will require ongoing maintenance.
* Long-term sustainability depends on documentation and community contributions.

The good news is that our architecture anticipates these challenges.
