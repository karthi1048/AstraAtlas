# ADR-002: Repository Structure & Development Workflow

**Status:** Accepted

**Date:** August 2026

# Context

AstraAtlas is intended to become a long-lived, open-source platform for trusted space mission and satellite information.

Although development begins with a single contributor, the repository is designed from the beginning to support future contributors, additional applications, automation, and independent services.

Rather than optimizing only for the current stage of the project, AstraAtlas adopts a repository structure and development workflow that can evolve without requiring major architectural changes.

This ADR documents those decisions.


# Decision

AstraAtlas will adopt a **monorepo architecture**.

Initially, only the backend application exists. As the project evolves, additional applications and shared resources will be added while remaining within a single repository.

The repository structure should evolve approximately as follows:

```text
AstraAtlas/
│
├── backend/
│   ├── app/
│   ├── tests/
│   ├── docs/
│   ├── pyproject.toml
│   ├── uv.lock
│   └── .pre-commit-config.yaml
│
├── frontend/
│
├── docs/
│
├── .github/
│
├── infrastructure/
│
├── scripts/
│
└── README.md
```

The exact directory structure may evolve over time, but the separation of responsibilities should remain consistent.


# Repository Principles

## 1. One Repository

All official AstraAtlas source code should remain within a single repository unless a compelling architectural reason requires otherwise.

This simplifies:

* issue tracking
* documentation
* versioning
* contributor onboarding
* project history


## 2. Independent Applications

Each major application manages its own tooling.

For example:

**Backend**

* Python
* uv
* FastAPI
* pytest
* Ruff
* mypy

**Frontend**

* Node.js
* package manager
* React
* frontend tooling

Neither application should assume the presence of the other’s runtime.


## 3. Shared Documentation

Repository-wide documentation belongs in:

```text
Docs/
```

Application-specific documentation belongs within the application itself.

Example:

```text
Backend/docs/
```


## 4. Infrastructure

Infrastructure configuration should remain separate from application logic.

Examples include:

* deployment configuration
* container definitions
* infrastructure-as-code
* monitoring
* automation


# Development Workflow

Every feature should follow the same workflow.

```
Create Branch
        ↓
Implement Feature
        ↓
Run Ruff
        ↓
Run mypy
        ↓
Run pytest
        ↓
Run pre-commit
        ↓
Commit
        ↓
Push
        ↓
GitHub Actions
        ↓
Review
        ↓
Merge
```

Quality verification should occur before merging into the primary branch.


# Quality Gates

A change is considered ready only when:

* formatting passes
* linting passes
* type checking passes
* tests pass
* CI passes

Future versions may introduce additional gates such as:

* security scanning
* dependency auditing
* performance validation
* documentation verification


# Tool Ownership

Development tools belong to the application that uses them.

Current ownership:

**Backend**

* uv
* pyproject.toml
* uv.lock
* pre-commit configuration
* Ruff
* mypy
* pytest

Future frontend tooling will remain independent.

Repository-wide tooling may later be introduced when multiple applications require shared automation.


# Git Strategy

Development should occur using feature branches.

Main should remain stable.

Recommended branch prefixes:

```
Feat/
Fix/
Docs/
Test/
Refactor/
Ci/
Chore/
```

Commits should follow Conventional Commits.

Examples:

```
Feat: add launch service

Fix: correct satellite parser

Docs: improve architecture documentation

Test: add parser unit tests

Ci: update backend workflow
```


# Testing Philosophy

Testing is part of development, not a final step.

New functionality should include appropriate automated tests whenever practical.

Coverage should be used as an indicator of confidence rather than a target to maximize.

AstraAtlas values meaningful tests over artificially increasing coverage percentages.


# Automation Philosophy

Manual repetition should be replaced with automation whenever practical.

Current automation includes:

* pre-commit hooks
* GitHub Actions CI
* automated formatting
* automated linting
* automated type checking
* automated testing

Future automation may include:

* deployment pipelines
* release generation
* dependency updates
* documentation validation
* security analysis


# Documentation Philosophy

Documentation is considered part of the product.

Architectural decisions should be recorded through ADRs.

Developer documentation should be updated whenever engineering workflows change.

User-facing documentation should evolve alongside platform capabilities.


# Evolution Strategy

The repository is expected to evolve in stages.

### Stage 1

Backend foundation.

### Stage 2

Frontend application.

### Stage 3

Shared documentation and repository tooling.

### Stage 4

Infrastructure automation.

### Stage 5

Additional services and integrations.

Each stage should build upon previous architectural decisions without requiring unnecessary restructuring.


# Consequences

## Positive

* Clear separation of responsibilities.
* Easier contributor onboarding.
* Predictable repository organization.
* Scalable architecture.
* Consistent development workflow.
* Strong engineering standards.

## Trade-offs

* Slightly more planning during early development.
* Multiple application environments to manage.
* Additional documentation maintenance.

These trade-offs are accepted because they improve the project’s long-term maintainability.


# Future Review

This ADR should be reviewed when:

* the frontend is introduced,
* repository-wide tooling is added,
* deployment architecture changes significantly,
* additional services are introduced.

Minor tooling updates do not require revising this ADR unless they change repository organization or development workflow.


# Conclusion

AstraAtlas is designed to be a long-term engineering project rather than a short-term prototype.

The repository structure and development workflow defined in this ADR prioritize maintainability, clarity, automation, and scalability.

Future contributors should be able to understand not only the codebase, but also the engineering practices that guide its evolution.
